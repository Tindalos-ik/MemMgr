# 基线实验设计与指标说明

## 1. 实验问题与控制方式

结果见[基线实测报告](../reports/baseline-report.md)，数值以该报告及原始运行记录为准。

| 实验问题 | 自变量 | 固定条件 | 观测量 |
|---|---|---|---|
| 文献规模变化时，导入成本与检索表现如何变化？ | small、medium、full 语料层级 | 同一批检索问题、分块与向量模型；检索 K=3、C=1 | 导入阶段耗时与吞吐，检索延迟、Recall@3、nDCG@3 |
| 输入预算对问答表现有何影响？ | 完整输入预算 B | small、前 8 个问题、K=3、C=1 | 实际输入/输出 token、阶段耗时、首次内容等待、吞吐 |
| 候选数量对问答表现有何影响？ | 文本块候选数 K | small、前 8 个问题、B=1024、C=1 | 文档级检索分数、实际证据和 token、问答耗时与吞吐 |
| 单序列服务面对更多客户端请求时如何表现？ | 客户端并发 C | small、前 8 个问题、B=1024、K=3；服务端 `max_num_seqs=1` | 应用排队、接纳后延迟、首次内容等待、批次吞吐 |

七组问答以第 2 组为参照，每个非参照条件只改变 B、K、C 中一个值。模型、硬件、软件版本、提示词规则、采样参数与输出上限保持一致。实验按固定次序执行，服务持续运行，跨组共享前缀缓存；没有随机化组别次序、重启清空缓存或测量独立冷启动。不同组的证据长度、输出长度和缓存状态也会影响延迟，不能将差值全部归因于某一个底层阶段。

## 2. 数据分层与抽样

- 数据采用 BEIR SciFact，原始查询是科学论断，语料为论文标题和摘要；来源、许可、下载校验和见[报告的数据说明](../reports/baseline-report.md#数据)。原始数据量与本轮选中的查询 ID 保存在 `data/scifact-baseline/metadata.json`。
- [`data.py`](../memmgr/data.py) 将同时存在于查询文件和 test qrels 的查询 ID 按字符串排序，用 `random.Random(7).sample` 抽取 30 个，再按字符串排序后写出；因此问答所取的“前 8 个”按 ID 字符串顺序确定。
- 对全部查询的正相关文献取并集作为必选集；其余文献 ID 按字符串排序，使用同一随机种子打乱，按各层规模补足。按规模由小到大累积文献集合后写出，形成 small、medium、full 三个嵌套子集，规模分别为 256、1500、5183 篇。各级共用所选查询及其官方 test 标签。
- 每级均保留所选查询的全部相关文献。`qrel_doc_coverage` 按查询—相关文献对计算：各查询在该级保留的正相关文献数之和，除以各查询全部正相关文献数之和（分母至少为 1）；同一文献关联多个查询时分别计数。`queries_with_relevant_doc` 为至少保留一篇相关文献的问题数。覆盖率衡量抽样是否丢失标签中的目标文献，与系统实际检索召回率分开解释。
- 独立检索使用全部 30 个问题。问答按 `queries.jsonl` 文件顺序取前 8 个，两个重复均使用相同问题及顺序，没有再抽取 8 个新问题。具体 ID 以运行目录的查询清单和数据副本为准。
- 该分层保证目标文献存在，同时增加其他候选文献；小语料含有针对所选问题保留的相关文献，不能据此估计任意随机小语料的检索质量。

## 4. 执行顺序与命令

环境安装、模型缓存路径和服务启动细节见[部署说明](deployment.md)。以下命令在 WSL 项目根目录执行，服务启动终端需持续保留：

```bash
export PYTHON="${PYTHON:-$HOME/mycode/vLLM/.venv/bin/python}"
export HF_HOME="$HOME/.cache/huggingface"
"$PYTHON" scripts/download_models.py
bash scripts/chroma.sh up
bash scripts/start-vllm.sh
```

另一个配置相同环境变量的终端执行正式入口：

```bash
"$PYTHON" -m memmgr --config config/baseline.json prepare
"$PYTHON" scripts/run_baseline.py
```

[`run_baseline.py`](../scripts/run_baseline.py) 依次执行 `index-small → retrieval-small → index-medium → retrieval-medium → index-full → retrieval-full → e2e-1 … e2e-7`。各检索/问答子进程先初始化编码器与集合，再预热，最后执行两次正式重复；每次重复结束后写入批次统计。调度脚本还保存应用源码 SHA256，并在正式执行期间检查源码是否改变。

子命令的真实形状如下，`CONFIG` 指执行目录中保存的该条件配置，不需要手动另造一套配置：

```bash
"$PYTHON" scripts/index_measured.py --config CONFIG --tier small
"$PYTHON" -m memmgr --config CONFIG retrieval --tier small --concurrency 1
"$PYTHON" -m memmgr --config CONFIG run --tier small --concurrency 1
```

索引与独立检索的 tier 按矩阵替换；问答并发按组替换为 1、2、4。实际解释器、配置路径、完整命令及执行结果以 `.agent/executions/execution-*/commands.json` 为准。子进程设置离线模型加载，`OMP_NUM_THREADS=2`，并使用脚本中固定的本机 `HF_HOME`；迁移时需核对该路径。

已完成索引会复用：复跑正式入口可能只测得索引查找，无法产生新的首次导入观测。首次导入来源通过 `.agent/state/index-run-registry.json` 关联；复现首次导入需使用独立的数据目录与持久化环境，保留原始数据和已有测量。已有索引的历史导入耗时不能记为本次复跑耗时。

### 输入预算、实际 token 与证据

[`prompt.py`](../memmgr/prompt.py) 按去重后的检索排名加入块文本。遇到超预算候选时，对该候选的字符前缀进行二分裁切，每次用 Qwen tokenizer 对完整聊天输入重新计数；随后结束加入证据，空前缀候选不纳入。若所有候选都较短，实际输入会小于 B，不会填充到 B。

| 字段 | 单位 | 定义 |
|---|---|---|
| `input_tokens_local` | token | 使用生成 tokenizer 渲染完整聊天模板后的本地输入计数 |
| `evidence_tokens` | token | 单独编码证据字符串的 token 数，含 `[DOC id]` 标记；不含系统提示、问题和完整模板，不能直接当作全部输入 |
| `input_tokens_server` | token | 流式响应 `usage.prompt_tokens`；报告的实际输入均值、最小值、最大值采用此字段 |
| `output_tokens_server` | token | 流式响应 `usage.completion_tokens`；报告输出量和输出速率采用此字段 |
| `output_tokens_local_estimate` | token | 仅服务端输出用量缺失时，对回答正文重新编码的估值，单列保存，不混入服务端实际用量 |
| `retrieved_doc_ids` | 文档 ID 列表 | K 个块去重后的文档排名，用于检索评分 |
| `included_doc_ids` | 文档 ID 列表 | 经输入预算裁切后实际放入提示词、且保留非空证据的文档 |
| `truncated` | 布尔值 | 组装时遇到超预算候选；不等于回答输出被截断 |
| `stream_chunks` | 内容块数 | 非空流式内容 delta 的数量；一块可含多个 token |

## 6. 耗时与吞吐定义

所有业务耗时使用单调时钟，单位为秒。设请求协程开始为 `t0`，取得应用信号量为 `t1`，发起生成流式 HTTP 请求为 `t2`，首个非空正文块到达为 `t3`，流式响应结束为 `t4`。问答的 E2E 结束记录紧随流式函数返回，包含少量调用返回开销。

| 报告量 / 原始字段 | 起止或公式 | 范围说明 |
|---|---|---|
| 应用排队 `queue_wait_seconds` | `t1 - t0` | 等待客户端信号量；每轮全部问题同时提交，后续问题可等待前面的请求完成 |
| 问答总耗时 `e2e_total_seconds` | 应用接纳 `t1` 至流式请求返回 | 含编码、检索、上下文组织、HTTP 与服务端等待/生成；不含应用排队和结果落盘 |
| 调度总耗时 `scheduled_total_seconds` | `t0` 至流式请求返回 | 约等于应用排队 + E2E；与两项分别读钟存在微小差异 |
| 首次内容等待 `e2e_ttft_seconds` | `t3 - t1` | 应用 TTFT；含检索和提示词组织，不含应用信号量排队 |
| 模型首次内容等待 `model_ttft_seconds` | `t3 - t2` | 生成接口 TTFT；含连接、传输与服务端排队/预填充，未拆出 GPU 内核时间 |
| 生成阶段 `model_total_seconds` | `t4 - t2` | 发起 HTTP 请求至响应关闭；包含首次内容之前的等待及后续内容传输，无纯解码时间拆分 |
| 查询编码 `query_embedding_seconds` | 提交编码线程前至编码返回 | 包含线程调度、编码锁等待及查询向量转换；并发时不能全部视为纯编码计算 |
| 数据库检索 `retrieval_seconds` | 查询向量就绪后提交 Chroma 查询至返回 | 含线程调度、客户端/网络与数据库处理；不含查询编码 |
| 上下文组织 `context_assembly_seconds` | 调用提示词组装前至组装结果记录完成 | 含模板渲染、预算核验、裁切及证据计数；候选文档去重先于该计时 |
| 独立检索总耗时 `full_retrieval_seconds` | 接纳后、编码开始前至去重与评分完成 | 含编码、数据库查询及少量结果处理；不含接纳前排队和批量落盘 |

对应的计时时序图和阶段实测表见[报告阶段耗时附表](../reports/baseline-report.md#阶段耗时与单请求速率附表)。

计时实现见 [`rag_batch.py`](../memmgr/rag_batch.py)、[`retrieval_batch.py`](../memmgr/retrieval_batch.py)、[`streaming.py`](../memmgr/streaming.py)。TTFT 在首个**非空正文内容块**触发，空角色包和用量包不触发；其测量粒度为流式块，不能推导精确首 token 的设备生成时刻。服务端等待尚未单独打点，不能用应用排队列代表 vLLM 等待时间。

### 单请求速率与批次吞吐

- 单请求生成阶段速率为 `output_tokens_server / model_total_seconds`，单位 token/秒；原始记录还保存 `output_tokens_server / e2e_total_seconds`。报告附表采用前者，并对逐请求速率求平均/中位数/P95。
- 每次重复的批次墙钟 `wall_seconds` 从 `asyncio.gather` 提交前计到所有请求返回，含应用排队和请求协调；问答还含逐请求 JSONL 写入，独立检索在批次结束后统一写文件。两种模式均不含预热与模型初始化。
- 成功请求吞吐为 `成功数 / 批次墙钟`，尝试吞吐为 `提交数 / 批次墙钟`，单位请求/秒。报告合并两次重复时，使用 `两批成功数之和 / 两批墙钟之和`。
- 整批输出吞吐为 `成功请求的服务端输出 token 总数 / 两批墙钟之和`，单位 token/秒；不包含预热输出。
- 批次吞吐采用真实墙钟，不能用平均单请求耗时取倒数替代，也不能对逐请求 token/秒取平均来代替批次输出吞吐。C>1 时请求时间相互重叠。

### 成功状态与统计

检索 `status=ok` 表示编码、查询和评分正常完成。问答传输成功但缺少服务端输入或输出用量时记为 `usage_missing`、`request_success=true`；异常记为 `failed`，另写 `failures.jsonl`。运行时批次统计可将 `usage_missing` 计为传输成功，[复算脚本](../scripts/summarize_baseline.py) 按 `status=ok` 计算正式成功数。本轮报告中的正式问答均有服务端用量，这两个口径在本轮一致；跨轮比较需显式核对。

平均数为逐请求值之和除以有效样本数，中位数为排序后的中央值（偶数样本取中间两项平均），P95 为最近秩 `排序值[ceil(0.95 × n)]`，下标从 1 开始。问答每组 n=16，P95 即该组最大值；检索每级 n=60，P95 为第 57 个值。报告两次重复的平均耗时分别只取该重复的正式记录。指标为空时不纳入该指标的 n。

30/8 个独立问题各重复两次，重复记录共享相同文本与标签，不能解释为 60/16 个独立问题。当前均值、中位数、P95 为描述统计，未提供置信区间或显著性检验。

## 7. Recall 与 nDCG 的真实计算

[`retrieval.py`](../memmgr/retrieval.py) 读取官方三列 qrels，仅将相关性分值大于 0 的文档放入相关集合 R，按二元相关性评分。Chroma 先取 K 个块，应用按原始文档 ID 保留最靠前的块，重复文档删除后压紧排名；没有继续取块补足 K 篇文档。

设去重后的排名前 K 项为 D，`rel(i)` 表示第 i 篇文档是否属于 R，排名从 1 开始：

- `Recall@K = |D ∩ R| / max(1, |R|)`。
- `DCG@K = Σ rel(i) / log2(i + 1)`，求和范围为 D 中实际存在的排名。
- `IDCG@K = Σ 1 / log2(i + 1)`，i 从 1 到 `min(|R|, K)`。
- `nDCG@K = DCG@K / max(IDCG@K, 1e-12)`。

K 在命名和理想排名分母中仍采用最初的块候选上限；实际文档数可小于 K。报告列出的 Recall/nDCG 为成功请求分数的算术平均。问答评分使用 `retrieved_doc_ids`，预算裁切后的 `included_doc_ids` 不参与评分；因此改变 B 不直接改变该项评分。相同问题重复测量会重复进入平均值。

这两个指标反映文档检索相关性，未评价生成回答的正确性、证据蕴含、事实完整性或断言支持/反驳分类。

## 8. 索引、启动与全流程耗时

| 量 | 定义与单位 |
|---|---|
| 文献数 `documents` | 导入语料中原始文档 ID 的数量，单位篇 |
| 文本块数 `chunks` | Chroma 最终 `collection.count()`，单位块；与分块累计的 `expected_chunk_count` 比较 |
| `new_chunks_this_attempt` | 本次实际新增的块数；部分导入续传时可能小于最终块数 |
| 初始化 `setup_seconds` | 从读取语料前开始，到模型、客户端和集合初始化完成，单位秒 |
| 文本准备 `preparation_seconds` | 各篇文献的整理、分块、构建待写记录耗时之和，单位秒 |
| 向量编码 `embedding_seconds` | 各批次 `embed(pending_documents)` 耗时之和，单位秒 |
| 写入 `write_seconds` | 从编码返回至 Chroma `add` 返回的累计时间，单位秒；包含向量转列表和客户端传输，未单独等待后台物理落盘 |
| 导入全流程 `full_seconds` | 从读取语料前至数量校验与试检索完成，单位秒；含初始化和各阶段，不含最终清单文件写入 |
| 包装计时 `measured_wall_seconds` | [`index_measured.py`](../scripts/index_measured.py) 调用 `index_tier` 前后墙钟，单位秒；还覆盖最终清单写入及函数开销 |
| 导入总吞吐 `chunks_per_second` | 最终块数 / `full_seconds`，单位块/秒 |
| 报告编码/写入吞吐 | 首次导入的块数 / 对应 `embedding_seconds` 或 `write_seconds`，单位块/秒；本轮为首次完整写入，不能照搬到续传运行 |
| 试检索成功 `probe_query.success` | 用首篇文献标题或正文前缀编码后查询，至少返回一个块；未要求返回 ID 必须等于首篇文献 ID |

索引实现见 [`index.py`](../memmgr/index.py)。各分项含计时外的循环、验证等开销，不能要求简单相加严格等于全流程。索引复用时包装器只记录 `lookup_wall_seconds` 并关联历史来源，不将历史清单里的编码/写入耗时当作本次新增工作。

报告的 vLLM 首次模型加载、权重加载耗时和模型加载显存来自服务启动日志，分别表示日志对应加载阶段的秒数和 GiB；它们与应用请求计时分开。模型加载显存也不同于整卡 `nvidia-smi` 已用显存。实验脚本全流程墙钟包含顺序运行子进程、初始化、预热、正式批次、结果写入和完整性复核等开销，不能用各组平均请求耗时相加替代；也不表示模型下载、数据下载和安装依赖的总时间。

## 9. 资源量与采样范围

[`resources.py`](../memmgr/resources.py) 在索引调用或检索/问答预热前启动后台采样，到该运行结束停止。检索/问答的编码器与 tokenizer 初始化发生在启动采样之前；资源观察包含预热和正式请求，未仅筛选正式请求窗口。首次服务模型加载需另看启动日志。

| 资源量 | 单位与统计口径 | 范围限制 |
|---|---|---|
| GPU 总显存、已用显存 | `nvidia-smi memory.total/memory.used`，MiB；已用取有效采样最大值 | 整张设备，含其他进程与服务预留，未隔离模型或单请求 |
| GPU 利用率 | `nvidia-smi utilization.gpu`，百分比；取最大值 | 设备采样窗口值，无法给出每个阶段的连续利用率 |
| WSL 内存、交换空间 | `psutil.virtual_memory().used`、`swap_memory().used`，字节；各自取峰值 | WSL 系统范围，不能归因于 MemMgr 单进程 |
| Python 进程树 RSS | 当前测量 Python 进程及递归子进程每次 RSS 求和，再取最大，字节 | RSS 可能重复计算共享页，未按独占内存去重 |
| vLLM 进程树 RSS | 配置 PID 及递归子进程每次 RSS 求和，再取最大，字节 | PID 必须对应当时的服务；缺失会写明未采集状态 |
| Chroma CPU | `docker stats` 的 `CPUPerc`，百分比；有效样本最大值 | 仅指定容器，沿用 Docker 多核口径，未换算为主机总体占比 |
| Chroma 内存 | `docker stats` 的 `MemUsage` 使用量部分，保留原始显示单位 | 报告采用 MiB；不得将容器上限当作实际使用量 |
| Chroma 卷大小 | 启动时 `du -sb /data` 的字节数 | 每次运行仅一次快照，未测增长曲线；报告未据此给出索引净增空间 |
| 磁盘 I/O | WSL 系统累计读/写字节数的末次减首次；报告合计各运行采样区间 | 含其他系统活动，不含区间之外和相邻运行间隙；未测 Chroma 独占 I/O |
| 实际采样间隔 | 相邻 `sample_start_monotonic` 之差，秒；首条无间隔 | 目标主机周期 1 秒、Docker 周期约 5 秒；采集耗时会拉长实际间隔 |

`1 MiB = 2^20` 字节，`1 GiB = 2^30` 字节。资源文件首行为采集元数据，后续行含起止时间、实际间隔与采集状态；缺失或失败采样不能补成 0。报告的有效间隔数及其最小/平均/最大值只统计非空实际间隔。各资源峰值独立取样，通常不在同一时刻；离散采样不能保证捕获瞬时最高值。

## 10. 回答引用、结束原因与功能边界

提示词要求使用证据、标注 `[DOC document_id]`、说明不确定部分；是否遵守需单独核对原始回答。行内引用遵从率以含该格式引用的正式回答条数除以全部正式回答条数；引用 ID 来源检查要求引用 ID 属于该请求的 `included_doc_ids`。这只能确认形式与来源，无法确认引用句是否真正支持回答。

`finish_reason=stop` 表示服务按结束条件停止，不保证回答正确或完整；`length` 表示达到输出限制，需检查是否截断。输入侧 `truncated` 与输出侧 `length` 各自独立。报告给出的引用比例、来源检查和达到上限的条数属于本轮回答观察，未开展人工全面标注或自动事实评分。

[报告功能检查](../reports/baseline-report.md#4-功能与服务检查)中的回归测试条数、语义操作、重启后状态和服务健康为功能验收记录：HTTP 200 表示服务接口可达，Chroma 心跳表示服务响应，集合数量表示持久化条目数。它们不构成生成质量评分，也不能证明长期稳定性或故障恢复性能。

本轮采用静态语料，没有 KV/记忆协同策略对照、在线记忆更新负载、7B 对照、GPU 嵌入对照、长对话或不同服务端并发设置。对应方向不属于本轮已验证结论。

| `.agent/runs/<run>/requests.jsonl` | 逐请求阶段、重复编号、计时、ID、回答、token 和结束原因；复算前筛选 `phase=formal` |

| `.agent/runs/<run>/summary.csv` | 运行时按重复输出的统计；合并两次重复的 P95 需从原始请求重新排序 |
| `.agent/runs/<run>/resources.jsonl` | 原始资源采样及缺失状态 |
| `.agent/runs/<run>/config.json`、`env.json`、`packages.json`、`code-snapshot.json` | 实际配置、环境、依赖版本和源码 SHA256；以对应运行实际保存项为准 |
| 检索/问答运行目录的 `dataset/`、`dataset-ids.json` | 测量使用的数据副本、查询顺序和文档 ID；索引包装器保存 ID 清单，数据由原路径定位 |
| 索引运行目录的 `summary.json` | 区分首次导入与复用，首次来源及包装层墙钟 |
| 运行目录 `logs/` 与服务启动日志 | 命令输出、运行起止和服务启动/加载证据 |

以执行目录中的 `commands.json` 为索引找到各个 run，不要按目录时间猜测正式来源。只复算已有原始记录时运行：

```bash
"$PYTHON" scripts/summarize_baseline.py .agent/executions/execution-YYYYMMDD-HHMMSS
```

将示例路径替换成实际保存的执行目录。该命令不重新发起实验，会写入当前工作目录的 `.agent/results/`：

- `baseline-results.json`：逐组指标、每次重复、整批统计、资源摘要和源文件 SHA256。
- `baseline-summary.csv`、`baseline-table.txt`：逐请求指标统计和简表。
- `baseline-batch-summary.csv`：每次重复的实际墙钟、成功数、token 总量和吞吐。
- `baseline-imports.json`、`baseline-import-summary.csv`：按正式集合及首次导入注册表追溯的导入数据。
- `baseline-cases.json`：筛选出的少量带有效来源引用且 `stop` 结束的样例，不等同于报告人工选取的问答示例，也不替代全部回答审查。

复算实现见 [`summarize_baseline.py`](../scripts/summarize_baseline.py)。报告中的 token 最小/最大值、引用格式遵从、资源实际间隔以及服务启动加载记录还需从对应 JSONL 或日志核对，不能仅依靠该脚本的均值/中位数/P95 输出。执行目录、运行目录与首次导入注册表需要一并保存；缺少这些本地产物时，仓库中的报告可用于阅读，无法从配置重新还原当次墙钟与原始回答。
